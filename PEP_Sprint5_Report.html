Sprint 5 Technical Report.

The Pedagogy Evaluation Platform is a web-based self-assessment tool built on Firmin's (2020) Techno-Pedagogical Practice framework. In Sprint 5 we delivered the two requirements Dr Firmin confirmed for the final development sprint: a participant can take the evaluation anonymously and then save the result to a new or existing account, and new accounts are verified with a 6-digit code sent by email. Dr Firmin also asked for a question bank during the sprint, so administrators can now edit the wording of the twenty statements from the admin dashboard. After the review build we added a forgot-password flow, archive instead of delete, and time on task, each tested and released.

01Summary

Sprint 5 had two confirmed requirements from the client: anonymous participation with the option to keep the result in an account, and verification of new accounts by an emailed code. Part-way through the sprint Dr Firmin also asked for a question bank, meaning the ability to see all twenty statements in the admin panel and edit their wording. We built and released that in the same sprint.

All three are implemented, deployed and verified against the twelve acceptance criteria we derived from the client's wording (Section 14). A thirteenth item, a forgot-password flow, was added on 13 October after we noticed the sign-in panel had no way to recover an account. It was built, verified and released the same day (Section 09). A fourteenth followed on 14 October when the client ruled that administrators must never delete an account, only archive it; it was built, verified and released the same day (Section 10). A fifteenth, on 15 October, asks the admin dashboard to show how long each participant spent on their evaluations; the data was already there, so it shipped the same evening (Section 11). As in Sprint 4, the rules live in the database rather than only in the browser. A stored anonymous result can be attached to an account only by a signed-in, verified user, only once, only within 24 hours of completing it, and under the same two-attempts-per-year rule as a normal submission. A statement's wording can be changed only by an administrator, and only the wording: category, order and weighting are locked by a trigger so the scoring model cannot drift.

02Sprint objectives

As confirmed by the client for Sprint 5, plus the request received during the sprint.

RefRequirement as stated
R1Anonymous user registration and result saving. The user starts the evaluation anonymously. At the end, the system offers to create an account; the completed result is saved to that account and can be viewed later.
R2Email verification code. When a user registers, a verification code is sent to the email address given; the account is verified by entering that code.
QBQuestion bank: see all questions in the admin panel and edit them.
Interpretation agreed during the sprint

We read R1 as "the result that was stored anonymously becomes the account's result", not "the participant retakes the evaluation after registering". That keeps the scores the participant has just seen on screen, and it means the offer belongs on the results page, after submission, rather than at sign-up. R2 already existed as the registration step (a 6-digit code rather than a link). We kept it, re-verified it, and extended it so it also works when someone registers from the results page. For the question bank we read "edit them" as editing the wording only. The category, order and weighting of a statement are part of Firmin's instrument and of the scoring model, so they stay locked (Section 08).

03Sprint process

How the sprint was planned, tracked and closed.

The client's two confirmed requirements set the sprint goal. The question bank was added when Dr Firmin asked for it on 12 October, and we delivered it the same day because it reused the admin dashboard and the database patterns we already had. A story closed only when its acceptance criterion in Section 14 had evidence: an automated database check, a browser check, or a read-only probe of the live system. We worked on feature branches and merged through pull requests. Database changes were applied in the Supabase SQL editor after the front-end release that tolerates their absence was live.

Sprint goal

Let a participant start with nothing to lose, with no account and nothing stored until they submit, and once they have seen their result let them keep it with one verified step. And let the client own the instrument's wording without being able to break its scoring.

05Anonymous start, saved result — R1

Nothing changes for the anonymous participant until the result is on screen. They begin without an account, nothing is stored while they answer (Sprint 4, R6), and one call to submit_assessment() stores the completed evaluation with no user attached. The completion screen now tells them where the result can be kept: "Your results are saved anonymously — on the results page you can save them to an account."

The offer

ConditionBehaviour
When the card appearsOnly when the participant is anonymous and the browser holds the session id that submit_assessment() returned — that is, the result exists on the server. A result that was saved on the device only (server unreachable) shows no card, because there is nothing to attach.
Create account & saveOpens the sign-in modal in claim mode on the Create account tab: title "Save your results", no Anonymous tab, button "Create account & save". Registration proceeds to the verification code (Section 07).
I already have an accountSame modal on the Sign in tab; button "Sign in & save results".

Refresh during verificationThe pending verification is kept for the tab, so the code panel reopens — still in claim mode — and entering the code still saves the result.

After sign-in or verification

The participant becomes the signed-in identity without the device clearing the result on screen (Section 12), and the page calls claim_assessment() with the session id. While it runs the card says "Saving this result to your account…". On success it shows "Saved to your account" with a link to the dashboard, and the anonymous email-capture card disappears because the account's address now receives results. If the participant already had an attempt this year, the card says so: the earlier attempt is kept as their previous attempt, exactly as after a normal second submission. If the attachment fails the card says why (Section 06) and still offers the dashboard. The account itself is fine, and their next evaluation will be saved to it automatically.

06Claim rules in the database

The attachment is one database function, claim_assessment(p_session_id) in sprint5-claim.sql. It runs with the caller's identity from the authentication token, so the browser cannot say who it is. We kept the random session id as the only credential. It is a version-4 UUID that submit_assessment() returns to the browser that submitted, nothing lets another caller list or guess unclaimed sessions (row-level security: users read their own rows, administrators read all), and a result can be claimed once.

RuleEnforcement
Only a signed-in, verified accountThe anonymous web role has no execute grant; inside the function an anonymous-token caller is also refused ("Sign in to save results to your account").
Only a stored, completed, still-anonymous resultThe session must exist, have completed_at set and user_id null; otherwise CLAIM_UNAVAILABLE. The row is locked for the duration so two claims cannot race.
Within 24 hours of completingOlder results answer CLAIM_EXPIRED. Long enough to decide after seeing the result; short enough that a session id left on a shared device does not stay claimable.
Attachuser_id is set to the caller and participant_email to the account's address (an anonymous email entered earlier is kept only if the account has none).
Two attempts per yearThe claimed result becomes the active result; the newest earlier attempt in the same calendar year (Australia/Melbourne) is kept as the previous attempt; anything older that year is removed — the same trim as on submission.
Return value{ session_id, year, previous_id, removed }, which the page uses to say whether a previous attempt was kept.
 
claim_assessment(p_session_id uuid) returns jsonb — security definer

 1  caller must be signed in and not an anonymous-token user          → 42501
 2  session must be completed and have no user yet (row locked)       → CLAIM_UNAVAILABLE
 3  completed less than 24 hours ago                                  → CLAIM_EXPIRED
 4  set user_id = caller, participant_email = account address
 5  keep the claimed result + the newest earlier same-year attempt; delete older same-year attempts
 6  return { session_id, year, previous_id, removed }
Why the browser keeps the id only for the tab

The session id is held in the tab's session storage, not in persistent storage. So the offer lives as long as the results tab on that device, and on the server for 24 hours. A participant who closes the tab before deciding cannot claim later. We chose that over leaving a claimable id behind on shared or public computers.

07Email verification code — R2

Creating an account sends a 6-digit code to the address given, and the account is usable only once that code has been entered. We use Supabase Auth's sign-up confirmation with the "Confirm signup" template set to emit the token rather than a link, using the branded template supabase/templates/confirm-signup.html. We read the live authentication settings on 13 October 2026: email confirmation is required and anonymous sign-ins are enabled. The same day we switched the authentication mailer from Supabase's built-in service, which only delivers to members of the project's own organisation, to custom SMTP through Resend. It sends as noreply@crmpilot.com.au on a domain whose DKIM and SPF records were already verified.

08Question bank

The twenty statements have always lived in the questions table, but the platform read the copy shipped in js/questions.js. The admin dashboard now has a Question bank panel between the demographic summary and the participant sessions. It shows every statement with its number, category, a text box with a character counter, when and by whom it was last edited, a Save button (Ctrl/⌘+Enter also works) and Restore original. Every page that shows a statement reads the database first and falls back to the shipped wording if it cannot be reached. That covers the home page, the questionnaire and review screen, and the admin responses view. The read is capped at 2.5 seconds so a slow connection never holds up the evaluation.

What can and cannot change

Only the wordingTrigger questions_guard_update raises "Only the wording of a question can be edited" if code, category, weight, order or active flag would change — so the scoring model (five statements per category, equal weights) cannot be altered from the dashboard or by a crafted request.

Research consideration

A reworded statement changes what later answers mean. The platform records who changed what and when, so a change can be reported. Whether an edit keeps a statement equivalent to Firmin's original is a research judgement for the client, not something the software can enforce.

09Forgot password — added and released 13 October

Not in the client's Sprint 5 list. We added it after the review build when we noticed the sign-in panel had no way to recover an account.

Until now a participant who forgot their password was locked out of their dashboard and history, with no way back except contacting an administrator. The sign-in panel now has a "Forgot password?" link. It asks for the account's address and emails a 6-digit reset code through the same sender as registration. The participant enters the code and a new password and is signed in. The flow works wherever the sign-in modal opens, including the results page in save-to-account mode, where the final button reads "Set password & save results" and the anonymous result is attached just as it would be after a normal sign-in.

10Archive instead of delete — added and released 14 October

A rule from the client after the review build: an administrator must never delete an account, only archive it.

The admin dashboard had a Delete button on every participant row, and a hidden "reset all test data" control, both backed by administrator delete policies in the database. We removed all of it. The row button is now Archive: the participant disappears from the table, the stats, the charts and the CSV export, and nothing is removed. A "Show archived" toggle reveals archived participants greyed out with an Archived badge that records when and by whom, and Restore brings them back. Archived participants can still sign in and use their dashboard; the archive only changes what administrators see.

11Time on task — added and released 15 October

A request from the client on the eve of the poster session: show on the admin dashboard how much time each user has spent.

We did not need a new table or a tracker in the browser. Since Sprint 4 every stored evaluation carries the moment its ten-minute session began and the moment it was submitted, because the server uses those two timestamps to refuse late submissions. The time a participant spent is simply their difference. The dashboard now shows it in four places: a Time column in the participant table, totalled across their completed evaluations and sortable, with the count and the latest attempt on hover; a Time on task card under Engagement with the average and the median per completed evaluation; a "Took m:ss" line on each session in the participant profile; and two columns in the CSV export. Archived participants are left out, as they are everywhere else.

12Architecture changes

The platform is still a static front end (HTML, CSS and vanilla JavaScript, hosted on Vercel) over Supabase (PostgreSQL, authentication, edge functions). In Sprint 5 we changed four parts of the client code so that sign-in can happen on any page and hand control back to that page.

ChangeWhy
The sign-in modal is rendered by js/auth.jsIts markup lived only in the home page, so no other page could open it. It is now injected by the script, and any page that loads auth.js and css/modal.css can open it. The home page lost 100 lines of duplicated markup (Figure 14).
IntentsThe modal is opened with an intent — start (default: go to the questionnaire) or claim (stay here and save the result). The intent sets the title, copy and button labels, hides the Anonymous tab, and survives a refresh during verification.
The ped:signed-in eventAfter a successful sign-in, registration or verification, auth.js dispatches a cancelable document event carrying the profile and intent. A page that cancels it owns what happens next (the results page saves the result); otherwise auth.js redirects as before. Pages no longer need to know how sign-in works.
PED.identity.adopt()begin() clears another participant's answers on shared devices — correct at the start, wrong when the same person is becoming an account holder with a result on screen. adopt() switches identity without touching the result on the device.
PED.questionBank (js/question-bank.js)sync() overlays database wording onto PED.QUESTIONS in place, so modules that already hold a reference see the new text; fetchAll(), update() and defaultText() serve the admin panel. Only text is ever changed on the client.

13Quality assurance

Defects and process issues found during development and release, all resolved before or on the day of release.

1  Becoming an account holder would have wiped the result from the device

Severity: high · Area: identity · Found in build, before release

The existing PED.identity.begin() clears the previous participant's answers, scores and session id whenever the identity changes. That is right on a shared device and exactly wrong for a participant creating an account to keep the result on screen: the first claim would have deleted the session id it needed. We added adopt(), which switches identity without touching the result, and begin() now calls it after its clearing step so the two cannot drift apart.

2  The sign-in modal could only be opened from the home page

Severity: medium · Area: front-end structure

The modal markup was part of index.html, so the results page had no way to show it. We moved it into auth.js as a single source, with the intent mechanism described in Section 12, and checked that the home page modal is unchanged (three tabs, close by ×, backdrop and Escape).

3  Question bank pull request merged into the wrong branch

Severity: medium · Area: release process · 12 October

The question bank was built on top of the Sprint 5 branch, so its pull request targeted that branch until GitHub retargets it to main when the base is merged. We merged it seven seconds after the Sprint 5 pull request, before the retarget, so it landed on the already-merged feature branch and not on main. We noticed within minutes because the live site still served asset version 2.2 when we expected 2.3, and fixed it with a third pull request from the feature branch to main containing the same fifteen files. The lesson is recorded in Section 17.

4  Test engine crashed on the migration's error handling

Severity: low · Area: test tooling

PGlite 0.3.x fails on the PL/pgSQL raise statement ("cannot resolve symbol setTempRet0"), which both migrations use for their refusals. We pinned the harness to PGlite 0.2.17, on which all 73 checks run.

5  Completion screen gave anonymous participants no hint about keeping the result

Severity: low · Area: copy

The status line now reads "Your results are saved anonymously — on the results page you can save them to an account", so the offer on the next page is expected rather than a surprise.

6  Home-page team roster out of date

Severity: low · Area: content · Carried from Sprint 4

The team section still named a member who had left. We corrected it (Product Owner Albin Roy, Tester Merajun Nabi) and released it on 12 October.

17Retrospective

What the team keeps, what it changes, and the actions carried into handover.

What worked

  • Reusing Sprint 4's rules instead of adding state. The claim applies the existing two-per-year trim and the existing session id; no new table, no new credential, and the dashboard needed no change.
  • Shipping the front end before the migration, with an honest message when the database is behind. Both releases were live and safe before the SQL was run.
  • Testing migrations in PGlite again. Fifty-three checks ran before either file touched production, including the refusals the browser never exercises.
  • Tester scripts as the acceptance evidence for what the team cannot observe itself. The four open criteria have a numbered step each, not a vague "test email".
  • A small, late request (the question bank) delivered the same day because the admin dashboard and the migration pattern were already there to extend.

What to change

  • Stacked pull requests: merge the base first and wait for the retarget before merging the next, then check the live asset version. The seven-second gap cost a third pull request.
  • Run the inbox test before the review, not after. Delivery is the one part of R2 the team cannot see from the code; it carried across two sprints and was closed the day after the release.
  • The Sprint 4 "next sprint" list assumed the handover items would be Sprint 5's scope; the client's requirements took precedence, as they should. Handover items need an owner and a date of their own rather than a place in a sprint that may be re-scoped.
