01Summary

Sprint 4 addressed six requirement areas raised by the client in sprint planning: a dashboard for signed-in users, storage and display of up to three years of evaluation data, correct handling of a current and a previous attempt (including the option to delete the previous one), year-to-year comparison presented with charts, a ten-minute limit on each evaluation session, and keeping an evaluation anonymous until it is completed.

All six are implemented, deployed to the live platform, and verified against the thirteen acceptance criteria derived from the client's wording (Section 13). The rules are enforced in the database rather than only in the browser, through a single write path for completed evaluations. The work also included a complete interface redesign and the recovery of the production database, which had become unreachable before the sprint began.

02Sprint objectives

As specified by the client for Sprint 4.

RefRequirement as stated

R2Store and display evaluation data for up to 3 years.
R3Handle two attempts/results. When there are two values/attempts, the system should handle the previous and current result properly. The user should have the option to delete/override the previous attempt. If the previous attempt is deleted/overridden, only the current attempt should be used as the active result.
R4Allow users to compare their current results with previous years/past attempts, including category-wise progress. Show whether the user's teaching-practice scores have improved, decreased, or stayed similar. This can be displayed using graphs/charts on the dashboard.

Interpretation agreed during the sprint

An early reading of R5 as an idle sign-out for account holders was replaced once the client's wording made clear that the ten minutes apply to each evaluation. An early reading of R3 as "one result per year, replaced automatically" was replaced by the client's "current and previous, with the option to delete the previous". Both earlier versions were superseded before release; the database migration was rewritten before it was run on the live system (Section 12, defect 1).

03Sprint process

How the sprint was planned, tracked and closed.

The team works in Scrum with the client as the single source of requirements. Sprint planning took the client's six numbered requirement areas (Section 02) as the sprint goal and broke them into the backlog below. A story closed only when its acceptance criterion in Section 13 had evidence — a database test, a browser check, a network trace or a read-only probe against the live system. Two clarifications of the client's wording (R3 and R5, Section 02) arrived mid-sprint; both were absorbed before release rather than deferred.

Sprint goal

Give returning participants a trustworthy view of their practice over time — current and previous attempts, three years of history, change by category — while keeping every evaluation private and unstored until it is complete.

  • A rule is enforced in the database wherever one exists, not only in the browser.
  • Automated database checks pass on a fresh schema and when applied over the previous migration.

04Production recovery

Context for the sprint: the live platform was not working when work began.

At the start of the sprint, sign-in and anonymous participation both failed on the live site. Investigation showed the fault was not in the application: the database host name returned NXDOMAIN from two independent DNS resolvers (Google and Cloudflare). The Supabase free-tier project had been paused after a period of inactivity, which removes its public address. The command-line access token recorded in the handover notes had also been revoked, so migrations could not be applied from the command line.

StepAction and result
DiagnosisDNS lookups, authentication health and REST probes confirmed the project was unreachable rather than misconfigured.
RecoveryThe project was restored from the Supabase dashboard and returned healthy (authentication settings unchanged: email sign-up and anonymous sign-in enabled).
MigrationsThe outstanding Sprint 3 migration and the Sprint 4 migration were applied in order through the SQL editor (Figure 9).
VerificationSix read-only requests against the live database confirmed every server-side rule (Section 13).
HardeningSign-in and registration now report "Can't reach the sign-in service" instead of a raw "Failed to fetch" when the backend is unavailable.
Lesson for handover

Free Supabase projects pause after one week without activity. A scheduled keep-alive request and a regular data export are recorded as outstanding items (Section 15).

05User dashboard and three-year history — R1, R2

Signed-in participants have a dashboard page (my-results.html, linked as "Dashboard" in the navigation). It is built from the participant's stored attempts, read under row-level security so each user can only ever load their own rows.

Dashboard contents

AreaContent
SummaryActive result (overall score and descriptor), overall progress label against the selected comparison, number of attempts and the date the oldest will be removed.
Current vs previousSelector for any earlier attempt; per-category rows with before and after scores, trend label and paired bars; comparison bar chart (Section 07).
Year-to-year progressLine chart and table of each year's result for up to three years (Section 07).
All attemptsEvery stored attempt with its status (Active result, Previous attempt, or year result), category scores, a link to its full report, and Delete for any attempt except the active result.
Other statesSigned-out, no attempts yet, and could-not-load messages, each with a clear next action.

Three-year retention

  • The dashboard query only reads attempts completed within the last three years.
  • The database function purge_expired_assessments() deletes any session older than three years. It runs on every submission and, where the pg_cron extension is available, daily at 03:15.
  • Deleting a session cascades to its responses and demographics, so no orphaned answers remain.

06Current and previous attempts — R3

RuleBehaviour
Active resultThe newest completed attempt is always the active result.
Previous attemptThe next most recent attempt in the same calendar year (Australia/Melbourne) is kept for comparison.
LimitAt most two attempts per year; submitting a third removes the oldest of that year.
Delete / override at submissionAfter a second attempt, the completion screen asks whether to keep both or delete the previous attempt.
Delete laterThe dashboard offers Delete on any attempt except the active result.
After deletionOnly the current attempt remains active; admin averages count one attempt per participant per year.

Enforcement

Both rules are enforced by database functions, not only by the interface. submit_assessment() applies the two-per-year limit, and accepts a p_replace_previous flag that removes all earlier same-year attempts in the same transaction. delete_previous_attempt() deletes one of the caller's own attempts and refuses when that attempt is the caller's most recent — so the active result cannot be removed, whether by mistake or by a crafted request.

07Historical comparison — R4

The comparison defaults to the previous attempt in the current year, or, if there is none, the most recent attempt from an earlier year. Any earlier attempt can be selected. Each category and the overall score receive one of three labels:

LabelRule
Improved ▲Score rose by more than 2 points.
Decreased ▼Score fell by more than 2 points.
Stayed similar ●Change of 2 points or less, so small fluctuations are not presented as progress or decline.

08Ten-minute session — R5

Behaviour

StageBehaviour
StartThe clock starts when the participant begins the evaluation. The start time is kept in the browser, so refreshing, closing the tab or opening a second tab does not reset it.
RunningThe remaining time is shown in the progress bar throughout the questions and the review screen.
WarningsAt two minutes the timer turns amber and at one minute red; each threshold is also announced to screen readers.
ExpiryUnsubmitted answers are cleared from the device, nothing is stored or emailed, and an expiry screen offers a new session or a return home. A participant returning after the time has passed sees the same screen.
Server checksubmit_assessment() rejects any submission more than ten minutes after the recorded start (plus one minute's grace for slow connections) with SESSION_EXPIRED, and rejects a missing or future start time.
Running
Final minute
Expired — nothing stored
Known limitation

The start time is reported by the browser. The server check prevents ordinary circumvention (refreshing, reopening, submitting late), but a technically skilled user could alter the reported start time. This is appropriate for a reflective self-assessment; exam-grade enforcement would need a server-issued session token, which would conflict with R6 for anonymous participants.

09Anonymous until completion — R6

Before Sprint 4, choosing "Continue anonymously" created an anonymous authentication account and a profile row, and beginning the questionnaire created a session row — so data existed before the evaluation was complete. Both behaviours were removed:

  • Anonymous participants are not signed in to the backend at all; any existing sign-in on the device is ended first.
  • No session row is created when an evaluation starts, for anonymous or signed-in participants.
  • Answers remain only on the participant's device until submission.
  • On submission, a single call to submit_assessment() stores the session and all twenty responses in one transaction, with no user attached for anonymous participants.

10Architecture and data model

The platform remains a static front end (HTML, CSS and vanilla JavaScript on GitHub Pages) over Supabase (PostgreSQL, authentication, edge functions). Sprint 4 moved the evaluation rules into the database so they hold regardless of the client.

Write path for a completed evaluation

submit_assessment(p_responses jsonb, p_started_at timestamptz,
                  p_replace_previous boolean default false,
                  p_participant_email text default null) returns jsonb

 1  reject a missing/future start time; reject if now − start > 10 min + 1 min grace
 2  require exactly the active questions (20), each answered 1–5; reject extra keys
 3  recalculate the four category scores from the answers (client scores are ignored)
 4  insert the session and all responses in one transaction
 5  signed-in only: remove abandoned in-progress rows; keep at most two attempts this
    year (or remove all earlier ones when p_replace_previous)
 6  purge sessions older than three years
 7  return { session_id, scores, year, previous_id, removed }
Database objectPurpose
submit_assessment()Only write path for evaluations. SECURITY DEFINER; executable by anonymous and signed-in roles.
delete_previous_attempt()Deletes one of the caller's own attempts; refuses the most recent. Signed-in role only.
purge_expired_assessments()Three-year retention. Not executable from the web roles.
idx_sessions_user_completedIndex on (user_id, completed_at) for history queries.
handle_new_user() (revised)Account-creation trigger; now frees an email held by an orphaned profile row (Section 12, defect 6).

Migration safety

sprint4-attempts.sql is idempotent and was tested both on a fresh schema and applied over its own earlier draft. A one-off clean-up keeps at most two attempts per user per year, removes abandoned in-progress rows older than a day, and applies the three-year purge.

12Quality assurance

Defects found during development and review, all fixed and re-verified before release.

1  Draft migration would have deleted same-year attempts

Severity: high · Area: database

The first version of the attempt migration replaced a user's same-year result automatically, and its clean-up step deleted all but one attempt per year — contrary to the refined R3. It was rewritten before being run on the live database, and the new version was tested applied over the old one.

2  Anonymous participation wrote data before completion

Severity: high · Area: authentication, persistence

Starting anonymously created an authentication account and profile row, and beginning the questionnaire created a session row, contrary to R6. Removed; verified with a network trace (Section 09).

3  Results email function could send arbitrary email

Severity: high · Area: edge function

The function accepted scores and a recipient from any caller, so it could be used to send emails with fabricated content to any address. It now sends only for a session completed in the last 30 minutes, uses the scores stored in the database, and escapes participant-supplied text.

4  Admin averages could count a participant twice

Severity: medium · Area: admin dashboard

With a previous attempt kept, both attempts entered the category averages. The admin dashboard now counts only the newest attempt per participant per year.

5  Home-page statement card overflowed on phones

Severity: medium · Area: responsive layout

At 375 px width the fifth answer option was cut off because grid items would not shrink below their content width. Fixed and verified on a 390 px viewport.

6  "Database error creating new user"

Severity: medium · Area: authentication trigger

Creating an account failed when an old profile row (whose account had been deleted) still held the same email, violating the unique email constraint. The account-creation trigger now frees the email from orphaned rows. Reproduced and fixed in a test database (fix-new-user-trigger.sql).

7  "Continue" button visible before answering; unclear outage errors; wrong category label in emails

Severity: low · Area: interface, email

A stylesheet rule overrode the hidden attribute; sign-in showed "Failed to fetch" during outages; emails labelled PD as "Professional Development". All corrected.

13Testing and acceptance

Database — 48 automated checks

The migration was executed with PGlite (PostgreSQL compiled to WebAssembly) against the full schema chain — supabase-setup.sql, admin-policies.sql, sprint3-demographics.sql, sprint4-attempts.sql — with mocked authentication functions for anonymous, signed-in and anonymous-token callers. The suite ran on a fresh database and over the earlier draft of the migration (24 checks each, every migration applied twice). All passed. Coverage: storage on completion only; expired, future and missing start times; grace period; incomplete, out-of-range, non-integer, string and extra answers; two attempts per year with the oldest removed; replace-previous; deleting a previous attempt; refusal to delete the active result; refusal across users; cascade of responses; three-year purge; permission denied on the purge function for web roles.

Browser — end to end

  • Dashboard with full history, a single attempt, and no attempts; switching the comparison; all three trend labels; deleting a previous attempt.
  • Timer at start, at two minutes, at one minute, expiry during a question and expiry on return; screen-reader announcements.
  • Anonymous run with request monitoring (Section 09); completion-screen keep/delete choice.
  • Sign-in behaviour with the backend unreachable; mobile layout at 390 px; 18 page states captured with no JavaScript errors.

16Retrospective

What the team keeps, what it changes, and the actions carried into Sprint 5.

What worked

  • Putting the evaluation rules in the database behind a single write path. Every rule held under the live probes, and the browser could be simplified because it no longer had to be trusted.
  • Testing the migration in PGlite before touching production. The suite caught the draft that would have deleted same-year attempts (Section 12, defect 1).
  • Verifying R6 with a network trace rather than by reading the code. It showed the anonymous sign-in and early session row that the code review had missed.
  • A shared design system. Seven pages were rebuilt in one release with a consistent look, and the admin dashboard inherited it for free.

What to change

  • Two requirements (R3, R5) were first built to an interpretation and then rebuilt to the client's wording. Confirm the wording in writing at planning before any migration is drafted.
  • The production database paused without anyone noticing. A live service needs a monitor, not a periodic manual check.
  • The team roster on the home page drifted from the sprint documents. Keep one source for team details and copy from it.
  • Sprint reports and slides were briefly published with the site. Documents that are not part of the product stay out of the published tree.
